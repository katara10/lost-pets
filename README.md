# Lost Pets — поиск потерянных животных

Веб-приложение для размещения объявлений о потерянных и найденных животных.

## Назначение

Пользователи публикуют объявления с местом и датой пропажи или находки, отслеживают
статус поиска, печатают листовки для расклейки и делятся объявлениями.

## Пользовательские сценарии

1. Просмотр ленты объявлений с фильтрами.
2. Просмотр карточки объявления.
3. Создание и редактирование объявления.
4. Печать листовки для расклейки.
5. Шаринг объявления в соцсети.
6. Личный кабинет со своими объявлениями.

## Экраны

| URL | Экран |
|-----|-------|
| `/` | Лента объявлений |
| `/ads/:id` | Карточка объявления |
| `/ads/new` | Создание объявления |
| `/ads/:id/print` | Листовка для печати |
| `/profile` | Личный кабинет |
| `/login` | Вход |
| `/register` | Регистрация |
| `*` | 404 |

## Backend

Серверная часть проекта реализована на Python с использованием фреймворка FastAPI, ORM SQLAlchemy и СУБД PostgreSQL.

### 1. Подготовка базы данных
Для работы бэкенда необходима установленная СУБД PostgreSQL. 
Создайте пустую базу данных (например, через pgAdmin или консоль psql).

Выполните следующий SQL-запрос:
CREATE DATABASE lost_pets_db;

### 2. Настройка переменных окружения
В папке backend/ создайте файл .env (он добавлен в .gitignore и не попадет в репозиторий). 
В нем необходимо указать строку подключения к вашей базе данных. 

Пример содержимого файла .env:
DATABASE_URL=postgresql://postgres:ваш_пароль@localhost:5432/lost_pets_db

В репозитории также присутствует файл .env.example с шаблоном настроек без секретов.

### 3. Установка зависимостей
Перейдите в папку backend, создайте виртуальное окружение и установите необходимые библиотеки.

Выполните команды в терминале:
cd backend
python -m venv venv

Для активации окружения используйте одну из команд (в зависимости от вашей ОС):
- Windows (Git Bash): source venv/Scripts/activate
- Windows (CMD): venv\Scripts\activate
- macOS/Linux: source venv/bin/activate

После активации установите зависимости:
pip install -r requirements.txt

### 4. Запуск сервера
Убедитесь, что вы находитесь в папке backend и ваше виртуальное окружение активировано. Запустите сервер разработки:

uvicorn app.main:app --reload

Сервер запустится по адресу: http://127.0.0.1:8000.


## Модель данных

Основная сущность проекта — **Объявление (Ad)**. На текущем этапе (ЛР №2) реализована одна таблица в базе данных.

**Таблица ads (SQLAlchemy):**
* id (Integer, Primary Key) — уникальный идентификатор объявления.
* type (Enum) — тип объявления: lost (потеряно) или found (найдено).
* species (String) — вид животного (кошка, собака и т.д.).
* name (String) — кличка животного.
* description (Text) — подробное описание (приметы, особенности).
* location (String) — адрес или район, где потеряно/найдено животное.
* date (DateTime) — дата пропажи или находки.
* status (Enum) — текущий статус: active (активно), found (найдено), closed (закрыто).
* contact_phone (String) — контактный телефон.
* contact_name (String, Optional) — имя контактного лица.
* created_at (DateTime) — дата и время создания записи в базе данных.


## Архитектура Frontend

В проекте используется упрощенная методология **Feature-Sliced Design (FSD)**. Полное соблюдение FSD не требуется, однако структура папок разбита по слоям ответственности, чтобы код было легко поддерживать и масштабировать.

### Слои приложения:

* **`app/`** — Настройка приложения. Здесь находится корневой компонент `App.tsx`, конфигурация роутера (`router.tsx`) и глобальные провайдеры (например, тема MUI).
* **`pages/`** — Страницы приложения (HomePage, AdDetailPage, AdFormPage и др.). Отвечают за композицию виджетов и фич под конкретный URL.
* **`widgets/`** — Крупные самостоятельные блоки интерфейса, которые используются на нескольких страницах (Header, Footer).
* **`features/`** — Пользовательские действия (фичи). Например, `AdFilters` (компонент фильтрации), `AdForm` (форма создания) или `ShareButton` (кнопка «Поделиться»).
* **`entities/`** — Бизнес-сущности проекта. Здесь описан тип `Ad` (`types.ts`), а также базовые компоненты для его отображения (`AdCard`, `AdList`), которые не завязаны на конкретную страницу.
* **`shared/`** — Переиспользуемый фундамент: UI-кит (кнопки, инпуты, лоадеры), вспомогательные утилиты (например, форматирование даты) и конфигурационные константы.

### Правила импортов:
Слои могут импортировать друг друга только «сверху вниз». Например, страница (`pages`) может импортировать компонент из `entities` или `features`, но сущность (`entities`) не должна знать о существовании страниц. Это исключает циклические зависимости и делает код предсказуемым.

## Аутентификация и авторизация

В проекте реализована система аутентификации на основе JWT (JSON Web Tokens) с использованием двух типов токенов: **Access** и **Refresh**. Это обеспечивает баланс между безопасностью и удобством пользователя.

### Процесс аутентификации:
1. **Регистрация:** Пользователь отправляет Email и пароль. Пароль хешируется с помощью алгоритма `bcrypt` (библиотека `passlib`) и сохраняется в БД. В открытом виде пароли не хранятся.
2. **Вход (Login):** При успешном вводе данных сервер генерирует два токена:
   * **Access Token** (срок жизни 30 минут) — используется для доступа к защищенным API-маршрутам.
   * **Refresh Token** (срок жизни 7 дней) — сохраняется в базе данных и используется только для получения нового Access-токена, когда старый истечет.
3. **Обновление токена (Refresh):** Если Access-токен истек, клиент отправляет Refresh-токен. Сервер проверяет его валидность в БД. Если токен действителен, выдается новая пара токенов (с ротацией: старый Refresh-токен отзывается).
4. **Выход (Logout):** При выходе Refresh-токен помечается в БД как отозванный (`revoked = true`), а клиент удаляет токены из `localStorage`. Даже если злоумышленник украл Refresh-токен, он не сможет его использовать.

### Эндпоинты API (`/api/auth/*`)

| Метод | Эндпоинт | Описание | Тело запроса | Ответ |
|-------|----------|----------|--------------|-------|
| POST | `/api/auth/register` | Регистрация нового пользователя | `{"email": "...", "password": "..."}` | Данные пользователя (без пароля) |
| POST | `/api/auth/login` | Вход в систему | `{"email": "...", "password": "..."}` | `{"access_token": "...", "refresh_token": "..."}` |
| POST | `/api/auth/refresh` | Обновление Access-токена | `{"refresh_token": "..."}` | Новая пара токенов |
| POST | `/api/auth/logout` | Выход из системы | `{"refresh_token": "..."}` | `{"message": "Logged out"}` |

### Защита маршрутов

**На стороне Backend:**
Маршруты создания, редактирования и удаления объявлений (`POST`, `PATCH`, `DELETE` для `/api/ads/`) защищены зависимостью `get_current_user`. FastAPI автоматически проверяет заголовок `Authorization: Bearer <Access_Token>` и возвращает ошибку **401 Unauthorized**, если токен отсутствует или недействителен. Публичное чтение (`GET /api/ads/`) остается доступным без авторизации.

**На стороне Frontend:**
Создан компонент-обертка `ProtectedRoute`. Он проверяет наличие токена в `localStorage` перед рендером защищенных страниц (например, `/profile`, `/ads/new`). Если пользователь не авторизован, он автоматически перенаправляется на страницу `/login`.

Для автоматического обновления токенов при истечении срока действия настроен Axios-интерцептор (`src/shared/api/client.ts`), который перехватывает ошибку 401 и незаметно для пользователя запрашивает новый Access-токен.
